# 开源工具横向评测（2026-10-28）

用户在决策卡 C03 的留言：「最好横向评测下效果。比较下哪个效果最好」（RAW-29）。本页记录这次评测的做法、结果和结论；结论用于 [agent-handoff](specs/agent-handoff.md) 的 AC-07。

## 怎么测的

- **机器**：作者的 Mac，Apple 芯片，内置盘 460 GB，当时剩约 40 GB；外接盘 T9。
- **安全**：所有工具只跑预演或只读命令，没有删除任何东西。工具下载在任务目录，测完删掉；Mole 运行时在主目录建的 `~/.config/mole` 和 `~/Library/Logs/mole` 也一并删了。
- **工具版本**：
  - Mole 1.65.0（GitHub 7.3 万星，GPL-3.0）
  - kondo 0.9（2.6 千星，MIT）
  - npkill 0.12.2（9.5 千星，MIT）
  - gdu 5.38.0（6.2 千星，MIT）
  - dust 1.2.6（1.3 万星，Apache-2.0）
  - mac-cleanup-py 3.4（2.4 千星）：需要 Python 3.11 以上，本机只有 3.9，没测
- **范围**：
  - 「项目构建产物」和「找大目录」都在任务目录 `~/RJJ-ELYS/elys-monorepo/worktrees` 上测。用 `du` 量出它在内置盘上的大小是 190.8 GiB；13 个任务在内置盘，3 天内都动过。
  - 「通用清理」在整个主目录上测。
- **原始输出**：在任务目录的 `one-click-evidence/tool-eval/`，评测脚本是 `eval-tools.sh`。

## 结果

### 找大目录

| 工具 | 用时 | 算出的总量 | 给 agent 用 |
|---|---|---|---|
| du（基准） | 75 秒 | 190.8 GiB | 只有总数 |
| gdu | 18 秒 | 190.8 GiB | 能导出 JSON |
| dust | 19 秒 | 190 GiB | 能输出 JSON |
| Mole analyze | 25 秒 | 188.2 GiB（按文件实际大小算） | 输出 JSON，自带最大文件清单，每项标明扫没扫全 |

三个工具都准，gdu 和 dust 略快。Mole 的大文件清单直接指出了问题：好几个任务里都有改过名的 Xcode 构建文件夹，比如 `DerivedData-flutter`、`.codex-w2b-DerivedData`，每份都有几个 GB。

### 项目构建产物（任务目录）

| 工具 | 找到的 | 会不会动 3 天内还在用的任务 | 能不能脚本化 |
|---|---|---|---|
| 资源看板 | 被 git 忽略、可重建的产物 65.6 GB | 不会：这些任务 3 天内都动过，一项也不删 | 能 |
| 资源看板计划（本次改进后） | 3 个任务里多余的 Xcode 构建副本 45 GB | 不会自动删，列进「需要判断」交给 agent | 能 |
| kondo | 59 个项目的 node_modules 等，12.6 GiB | 会：默认不看任务最近有没有在用，确认后就删 | 只能逐项回答 y/n |
| Mole purge | 没有可清的（它只挑放旧了的项目） | 不会 | 能（--dry-run --yes） |
| npkill | 跑不起来：必须在真正的终端界面里操作 | — | 不能 |

### 通用清理（整个主目录，Mole clean 预演）

| 部分 | 大小 |
|---|---|
| 和开发无关的：App 缓存、日志、Chrome 缓存、帮助和地图缓存等 | 约 3.8 GB |
| 没在用的 iOS 27.1 模拟器系统 | 7.9 GB；资源看板的「等你确认」也找到了同一项 |
| 废纸篓 | 没给终端「完全磁盘访问」，读不到；资源看板也一样 |

预演还表明，**Mole 会把资源看板特意保留的共享缓存一起清掉**：

- Xcode 的 DerivedData：69 个项目，15.3 GB，其中编译缓存 7.7 GB、模块缓存 1.8 GB；
- npm 缓存：1.1 GB；
- Go、pip 缓存：预演只写了「会清理」，没给大小。

这些都是放在 T9 上、给各任务共用的缓存，清掉后每个任务都要重新下载、重新编译。Mole 还自动把 `~/RJJ-ELYS` 加进了它的项目扫描范围。

## 结论

1. **只接 Mole**（维持 C03 的 A）。它是唯一覆盖「通用清理」的，找大目录又准又能输出 JSON，还自带给 agent 用的 skill。
   - gdu、dust 只是快一点，没有多出能力。
   - kondo 不看任务是否还在用。
   - npkill 不能被 agent 调用。
   - mac-cleanup-py 要更高版本的 Python。
2. **调用 Mole 前必须先写白名单**（C04 的 A）。这次实测证明，不写的话 Mole 会清掉 T9 上的共享缓存。写的时候要把 Mole 自己的默认白名单一起保留：白名单文件一旦存在，就会替换掉它的默认保护。
3. **分工**：
   - 资源看板专做别人没做的：判断任务是否还在用、找出同一任务里多余的构建副本、外接盘、共享缓存、按目标出计划。
   - Mole 负责系统和 App 那部分。
   - 两边都找到的（例如没在用的模拟器系统），以资源看板的「等你确认」为准。
4. **这次带来的改进**：资源看板现在能认出改过名的 Xcode 构建文件夹（名字里带 DerivedData 就算），计划里「需要判断」从 30 GB 增加到 45 GB。
